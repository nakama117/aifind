## 2. 产品定位与品牌决策

### 2.1 唯一主方向

AIFIND 面向日本用户，帮助其知道重要 AI 变化、找到合适产品、比较真实差异，并按照可复现的步骤用起来。不是所有行业资讯门户，不是几千款工具目录，不是企业技术采购数据库公司。

品牌建议：`AIFIND`。约定日文读法：`アイファインド`。主标语：`いま使えるAIが、見つかる。`。解释句：`AIを知る、比べる、使いこなす。`。候选主域名：`aifind.jp`。

域名可注册属于用户当时的查询结果，未完成注册或商标清查。不得声称“域名已经购买”“没有品牌冲突”“必然容易拼写”。AIFIND 为 6 个拉丁字母，AISIGNAL 为 8 个；短是客观差异，记忆度仍需目标用户测试。

### 2.2 AIFIND 与 AISIGNAL 的取舍

| 维度 | AIFIND | AISIGNAL |
| --- | --- | --- |
| 核心动作 | 寻找产品、比较、发现使用方法 | 观察变化、追踪市场信号 |
| 最新范围匹配 | 产品发现与实际使用占核心，更贴合 | 若重新成为监控情报产品会更贴合 |
| 商业路径 | 与试用、比较、选型页面衔接自然 | 与新闻订阅、趋势简报衔接自然 |
| 局限 | 通用组合，存在重名与品牌搜索混淆风险 | 也可能与投资信号、分析类产品混淆 |
| 结论 | 优先候选，但商标与注册是上线门禁 | 不再作为第一阶段优先主品牌 |

选择 AIFIND 是范围变化后的产品判断，不是预测其转化率更高。域名或品牌词不替代内容质量与获客验证。

## 3. 用户、首发聚焦与范围

### 3.1 目标用户与任务

| 用户 | 实际问题 | 核心页面 | 成功信号 |
| --- | --- | --- | --- |
| 日语知识工作者 | 想用 AI 总结资料、写作和处理日常工作 | 产品、场景、教程 | 找到可用工具并完成一个任务。 |
| 个人创作者 / 营销人员 | 预算有限，想比较内容制作方案 | 比较、用途、工作流 | 明白适用边界并试用。 |
| 开发者 | 想比较编码工具、安装、权限与成本 | 编码产品簇、实测教程 | 复现实测步骤或作出工具选择。 |
| 小团队负责人 | 关心协作、套餐和数据使用条件 | 产品事实与条件比较 | 明白哪些条件尚需向厂商确认。 |

首发不平均覆盖所有人群。建议以“个人 / 小团队的日语资料研究、写作与办公工作流”为主要编辑切口，编码工具为第二实验簇。利用负责人已有日语与电商运营经验做真实任务，不编造技术资历或测试经验。影音、HR、法务、医疗等不同时扩张。

### 3.2 分期范围

| 层级 | 必须做 | 不在此阶段做 |
| --- | --- | --- |
| P0：公开试运行 | 稳定新闻入口、8–12 个完整产品、3 个比较、6 个实测教程、3 个用途页、搜索、联系/政策页 | 用户账户、评论、复杂推荐、付费订阅、企业数据库。 |
| P1：90 天验证 | 经质量门禁扩大至 20–30 产品、8–10 比较、6–8 用途页、18–24 教程；周报订阅 | 为凑 100 页批量生成、默认多站多语言。 |
| Stretch | 若人工容量足够，扩到原讨论的 70–120 个常青页面 | 不以这个数量作为上线、成功或排名条件。 |

## 4. 信息架构与页面体验

### 4.1 一级导航

V1 显示：`今日のAI`、`AIを探す`、`比較する`、`使い方`、搜索。`ランキング` 在有明确方法和足够数据之后再显示，不用虚构榜单占位。企业案例、周报、政策、研究等放次级入口。

首页模块顺序：品牌与任务搜索 → 三个动作入口 → 今日重要 → 用途 → 核心产品 → 比较 → 实测教程 → 周报。急上升可放在今日重要旁的次模块，数据不足时显示“観測データを蓄積中”或隐藏。

今日重要最多 5–8 条，不足则少发；不得把昨日内容伪装成当日新闻。热门产品初期应写“編集部が選んだ基本ツール”，不能把编辑挑选叫用户人气。

### 4.2 路由契约

| URL | 页面角色 | 默认策略 |
| --- | --- | --- |
| / | 首页 | index；所有核心入口为普通可抓取链接。 |
| /news/、/news/:slug | 新闻与有实质增量的事件 | 独立新闻选择性 index。 |
| /products/、/products/:slug | 产品目录与事实中心 | 完整已发布产品 index。 |
| /compare/、/compare/:slug | 经过编辑的比较 | 未编辑组合不生成公开页面。 |
| /categories/:slug | 用途与候选产品 | V1 同时承载“找产品 / 推荐”，避免重复类别页。 |
| /howto/、/howto/:slug | 教程与工作流 | 实测或清楚标明资料整理，满足门禁才 index。 |
| /cases/:slug | 轻量公开案例 | 后置；未知事实不补全。 |
| /search?q= | 站内搜索 | noindex, follow；限制参数组合。 |
| /newsletter/ | 周报介绍与订阅 | 介绍页可 index；确认页 noindex。 |
| /about、/editorial-policy、/affiliate-disclosure、/privacy、/terms、/contact | 身份、政策与联系 | 真实信息；不得冒充日本法人。 |
| /admin/*、/preview/* | 后台、预览 | 认证、私有缓存策略；noindex 不能替代鉴权。 |
| /go/:linkKey | 允许条件下的商业出站链接 | 非 SEO 页面，受控目的地址。 |

价格 V1 放在产品页 `#pricing`，不同时生成 `/pricing/claude` 等重复内容。出现独立搜索需求和足够深度后，才以编辑决定拆分，并整理 canonical 与内链。

上游 `/all`、`/hot`、`/topics`、报告页和 item/story 路由须 Gate 0 清点。保留已有有效链接；确需改 URL 时建立一对一永久跳转。不得批量跳首页，不得把两套路由作为两个可索引副本。[R3]

### 4.3 视觉与交互

设计风格是清晰的工具型媒体：优先搜索、表格、标签、明确来源与更新时间，不使用无意义 AI 装饰图。公开语言为自然日语，错误、空态、移动菜单也必须日文化。后台可以使用中文说明配稳定英文字段。

移动端比较表允许横向滚动并固定表头；键盘可访问，颜色不是唯一信息载体。未知显示“未確認”，否定显示“不対応”，不要用同一个灰色叉号混淆。没有数据时不显示模拟数字。

## 5. 页面模板与内容硬规则

### 5.1 产品页

按顺序包含：一句话用途、适合/不适合的任务、Japan 可用性、日语分项、套餐与价格、主要功能、限制、核验来源、实测方法入口、相关比较、教程、最新已确认变化、官方/联盟动作。

产品事实必须有字段级证据、市场范围、套餐范围与核验时间。产品、模型、套餐、销售渠道分开：同一模型在不同产品内的权限不同；Web 与移动端价格不能互相替代；年度折算月价不是月付价格。

V1 不发布没有方法依据的 9.3/10 评分。“適している”属于编辑判断，应说明任务和依据，不声称一般用户永远选 A、编码永远选 B。

### 5.2 比较页

包括：比较对象和版本、测试日期、共同任务、套餐/限制、动态事实表、实测结果、分别适合的人、不适合的人、不可比条件、结论与证据。

公开结论必须由当期证据支持。事实更新后，旧实测结论可能过期；系统只同步事实表并标记 `needs_retest`，不得悄悄重写“最佳产品”。至少说明测试输入、执行步骤、错误判据、重复次数或单次观察局限。

### 5.3 用途 / Best 页面

每页围绕一个明确问题，例如日语资料研究、低预算会议记录、个人写作。以 3–5 个可认真比较的候选开始。每个推荐给出适用条件、排除理由和进入更深页面的入口。不根据佣金、厂商付费或公开案例数量排序。

类别标签是检索组织，不是现成 SEO 页面生产器。新建可索引类别必须有独立用户问题、足够事实、编辑选择与实际内链。

### 5.4 教程 / 工作流

固定模板：任务结果 → 必要账号与套餐 → 测试环境/日期 → 素材与输入 → 逐步操作 → 结果展示 → 常见失败 → 限制/费用 → 可替代方案 → 来源与修订。

亲测文章需要实际操作截图或可复现记录。使用自有或获授权的测试素材，截图脱敏。未亲测内容可发布为“公式資料に基づく解説”，不得使用“AIFIND検証済み”。验证标签记录产品、版本、套餐、任务和日期，不等于产品所有能力都被验证。

### 5.5 新闻与轻量案例

新闻保存来源、原始发布时间、事件发生时间（未知可空）、采集时间、摘要和实体链接。正文不是另一家媒体全文的翻译副本。重大新闻可单独成页；例行修复进入产品变化日志；其他采集只作后台材料。

轻量案例只保存企业、产品（明确才填）、用途、原文阶段、日期与来源。不得用真实企业名填示意供应商、人数或效果。PoC/生产状态与部门/全社范围是两个维度；“全社试用”不等于生产落地，未再发公告不等于停用。

## 6. 内容生产计划与选题管理

### 6.1 先建设两个可维护主题簇

主要簇：资料整理与日语办公，包括 PDF/网页材料整理、带出处写作、会议记录、表格分析。实验簇：AI 编码工具的初学者安装、权限、成本与实际任务。产品名只是候选实体，不代表其当前功能或联盟可用性已核验。

前台不需要每款产品都拆成 pricing、free、Japan、alternatives 五个薄页。先在产品页集中回答；深度任务或真实选择问题才建独立页。

### 6.2 首批常青内容清单（30 页起步）

| 批次 | 具体页组 | 页面数与类型 |
| --- | --- | --- |
| A | ChatGPT、Claude、Gemini、NotebookLM、Perplexity、Cursor、Claude Code、GitHub Copilot | 8 个产品事实页；现状逐项核验。 |
| B | 资料研究；文档写作；AI 编码入门 | 3 个用途页。 |
| C | 同一日语资料任务的 ChatGPT/Claude；NotebookLM/Perplexity；Cursor/Claude Code | 3 个比较页，不预定赢家。 |
| D | PDF 任务、出处核查、表格核验、日语措辞修订、会议待办提取、代码变更审阅 | 6 个任务型实测教程。 |
| E | 免费版限制核对、订阅与 API 区别、上传前脱敏、不同产品交接、结果验证、失败排查 | 6 个解释/工作流页。 |
| F | 首选主题的 2 个真实细分任务与 2 个真实对比 | 4 页，基于初期用户问题确定。 |

30 页是编辑组合示例，不包含政策页和新闻。扩到 50–70 页时优先补已有产品的真实问题；70–120 页为有额外编辑容量的伸展目标，不强制。

### 6.3 投入与更新节奏

建议每周规划约 16–22 小时内容/运营时间，另计初期开发；实际工时须连续两周记录后调整。该范围为工作预算，不是能够自动完成的承诺。

每周可从 2 篇实测教程、1 篇比较/用途页、核心产品复核和一封周报开始。新闻采用工作日精选、小条目不单独成页；若审核超时，减少数量而不降低证据要求。

内容看板字段：任务、用户问题、所属产品、意图、证据准备、测试成本、商业资格、编辑状态、下次复核、真实效果。机会优先级是判断工具，不是把未知搜索量乘成伪精确分数。

## 7. 技术架构与 CMS 决策

### 7.1 选择：AIHOT 上的模块化单体

继续使用现有 TypeScript / React Router SSR / Fastify / PostgreSQL / pg-boss。一个仓库、一个核心 PostgreSQL、web/api/worker 三个职责分明的进程，增加轻量 AIFIND Admin。访客页面只读已发布数据，不实时请求大模型。[R1–R3]

```text
访客 / 搜索引擎
    → HTTPS / 可选 CDN
    → React Router SSR (web)
    → Fastify API → 统一公开读取策略
    → PostgreSQL 已发布事实与内容

信息源 → AIHOT worker / pg-boss
       → 原始记录 / 事件 / 候选变更
       → 管理员审核 → 发布事务
       → 产品事实 + 内容修订 + 公开变更

图片：持久卷或对象存储；数据库保存元数据
邮件：第三方服务负责订阅、退订与送达
```

### 7.2 为什么暂不引入 CMS 产品

| 方案 | 真实优势 | 当前取舍 |
| --- | --- | --- |
| 传统 WordPress | 文章编辑、媒体库、生态成熟；可做结构化内容 | 对只做文章的网站可合适，但本项目会与既有采集和产品事实库重复。 |
| Headless WordPress | 编辑体验成熟，前端自由 | 双运行时、双数据库及缓存/发布同步增加个人运维负担。 |
| 独立 Headless CMS | 关系模型、编辑/版本功能可复用 | 并非“不支持关系”；当前代价是新系统接入和与专用审核流程的协调。 |
| AIHOT + 小型自研 Admin | 同一事实库、候选审核与发布规则可直接复用 | 选定；必须补基本编辑/修订/权限，不能把数据库 CRUD 当完整 CMS。 |

自研不是无成本。给编辑后台设验收：能保存草稿、上传截图、预览、恢复上版、关联产品、发布/撤回。若一个迭代后还不能完成真实编辑任务，应审查成熟编辑组件或兼容数据库的管理工具；必须以书面 ADR 调整，不自动再造第二套数据源。

### 7.3 拟新增模块

建议先一个 `modules/aifind/` 工作区，内部按 catalog、editorial、changes、commercial 划分，不为每张表拆一个服务。后续模块是否再拆，取决于真实依赖。

```text
modules/aifind/                # 拟新增
  package.json
  module.ts                   # URL / 路由声明
  server.ts                   # API / worker / 插口注册
  web.tsx                     # 页面、导航和后台组件注册
  contracts/                  # 对外 DTO 与校验
  catalog/                    # 产品、套餐、事实
  editorial/                  # 文章、比较、发布与修订
  changes/                    # 候选发现、审批与变更应用
  commercial/                 # 外链、归因接口
  publication/                # 模块公开投影；受统一规则约束
  admin/
  migrations/
  tests/
```

这是目标目录，不是已存在路径。模块迁移按上游全局文件名排序规则编号，避免与核心重号；框架通用改动才进 `database/migrations/`。通过 `site/modules/` 三份清单注册。所有公开出口必须整合上游 publication 统一范围与撤回规则，不能因新模块出现第二种可见性。[R1、R3]

## 8. 数据模型：小而完整的业务对象

### 8.1 总体约束

下面使用 `af_` 前缀表示拟新增模块表，防止与 AIHOT 已有文章、来源和事件表冲突。Gate 0 必须读取真实迁移并出映射，不能凭聊天里的 news/events/sources 名称建重复表。

主键用现有仓库约定；新表若无约定使用 UUID。时间使用 `timestamptz` 保存时刻；纯日期使用 date。金额用 numeric/decimal，不用浮点数。核心关系用外键，数组仅用于小型已校验展示配置。

## 9. 信息采集、证据与时效

### 9.1 信源登记

登记每个来源的类型、URL、发布主体、地区、语言、抓取频率、版权/使用约束、最后成功时间与错误。初期 20–30 个优先来源：官方更新/帮助/价格页 + 日本官方入口 + 少量可信媒体发现源。

来源权威按具体主张判断：厂商公告能支持其开放动作和标价，不自动证明性能优于别人。媒体用于发现与上下文；关键价格/权限优先回原始资料。付费墙、登录受限、robots/条款限制的内容，不绕过访问控制。

产品变化并不总是新闻：价格、帮助中心和 changelog 应单独进入变更监测。此处需要新增连接或监控任务，不能声称 AIHOT 现有 RSS 自动覆盖所有事实。

### 9.2 时间字段

必须区分 `published_at`（公告发表）、`effective_at`（官方明示生效）、`retrieved_at`（抓取）、`verified_at`（人工确认）、`tested_at`（实测）。不明的生效日为空，不拿抓取日填充。

用户看到“最終確認”只说明检查日期，不说明所有功能实测。网页 `dateModified` 只在实质内容变化时更新；仅重新抓取或人工看过不算修改。

### 9.3 时效管理

建议初始复核间隔：核心价格/访问条件 14 天，其他产品事实 30–60 天，教程重大更新后立即排队或至少季度复查。只是运营默认值，若人力超限先减少核心产品数量。

已过期字段保留历史值和日期，并显示“要再確認”；无法访问不直接改为“不支持”。比较依赖中的一个关键事实变更后，事实表展示新版、编辑结论显示待复核，直至审核完成。

## 10. 变更处理流水线

### 10.1 输入到发布

```text
采集 → 原始条目去重 → AI 相关预筛 → 产品实体候选
     → 变化分类 → 受控字段抽取 + 证据定位
     → 结构/语义校验 → 冲突检测 → 人工审核
     → 原子应用 + 修订 + 审计 + outbox
     → 公开事实更新 / 缓存失效 / 教程复核提示
```

变化类型 V1：pricing、plan、availability、feature、api、model_relation、lifecycle。模型输出是提案，不是写入指令；不允许任意 URL、SQL、表名或路径从输入透传到执行层。

### 10.2 候选契约示例（纯合成，不是现实价格）

```json
{
  "productId": "example-product-id",
  "baseRevision": 4,
  "changeType": "availability",
  "changes": [
    {
      "field": "japan_web_availability",
      "oldValue": "unknown",
      "newValue": "limited_rollout",
      "market": "JP",
      "channel": "web",
      "evidenceId": "example-evidence-id"
    }
  ],
  "state": "pending_review"
}
```

未知产品、未知字段、币种缺失、套餐范围模糊、引文定位失败均转人工，不自动补全。模型的自报 confidence 不作为自动发布依据。

### 10.3 语义校验

金额不只检查数字是否出现在原文；还检查币种、计费周期、套餐、渠道、税和地区。功能声明不只检查公司名；要定位到正确产品与套餐。官方“滚动开放”只能保存有限开放，不能写所有日本账号已可用。

证据采用必要短摘录与段落定位，保持原文语义；不允许把原文不同段落拼成一句假引文。实体不确定时保留候选列表，不把母公司/子公司或两个 Copilot 产品强行合并。

### 10.4 状态、事务与并发

候选状态：detected → pending_review → approved / rejected；approved → applied。Phase 2 已确定的流程为 Candidate → Approve → Apply to Draft → Human Review → Publish。批准与应用不切换 Published；应用只修改 Draft，并在同一事务内写审计。公开版本只能由管理员单独执行 Publish。

MUST 校验候选的基础 Published 版本、目标字段和 Draft revision。数据库现行版本或目标事实不同则返回 409，保留候选与 Draft 原状，由人重新判断。重复应用不能重复写入事实或审计。

approved 是可审计的待应用状态；applied 表示已经应用到 Draft，不代表公开。回滚通过新修订恢复旧值，不删除历史。Resolver / Detector、异步任务和通知仍属于后续阶段。

## 11. AIFIND Admin / 编辑流程

### 11.1 后台最小功能

| 页面 | 必要动作 |
| --- | --- |
| Dashboard | 新闻候选、事实变更、过期项、任务失败、预算用量。 |
| Products | 建立/编辑身份、事实、套餐、来源；草稿预览；发布/撤回。 |
| Change Review | 当前值 / 新值 / 来源并列；批准、应用到 Draft、拒绝；冲突返回 409 并保留原状态。 |
| Editorial | Markdown 编辑、自动保存草稿、截图上传、预览、修订恢复、关联产品。 |
| Compare / Categories | 选择产品、受控比较维度、编辑结论、实测版本与复核状态。 |
| Outbound Links | 官方/联盟目的地、许可、有效期、停用与回退。 |
| Sources / Jobs | 复用上游试抓、频率、错误与预算入口。 |
| Newsletter | 草稿、测试发送、最终发送确认与回执。 |

同一个管理员也需要鉴权、CSRF 防护、草稿隔离和审计；“V1 不做账户”是指不新建普通读者账户，不是后台无登录。

### 11.2 编辑发布状态

`draft → in_review → published → withdrawn`。退回审核可回 draft。修改已发布文章建立新草稿，公开页面继续读旧发布版。出版时间只在首次发布设置；修订时间随实质更新变化。

预览使用认证会话或短期签名令牌，`Cache-Control: private, no-store`，不进 sitemap。搜索、相关推荐、JSON-LD、RSS/API 均不得泄露草稿。撤回同时从所有出口移除，避免只在页面隐藏而 API 继续暴露。

以下是拟新增的站点内部接口，不是收费开放 API。路径最终与上游模块注册审计保持一致，不改变既有 `/api/v1/` 契约。

| 接口 | 作用 | 边界 |

## 13. SEO、渲染、缓存与链接

### 13.1 搜索质量原则

允许用 AI 辅助不等于可批量制造没有信息增量的页面。采用真实测试、受控事实、适用限制、来源与日期作为质量门禁，不以字数、结构化数据数量或框架名称作为排名保证。商业内容也必须有独立价值。[W1、W6]

所有可索引页面首次 HTML 应包含主要正文、产品事实、title/canonical、正常链接和适当结构化数据。后加载用于交互，不隐藏核心信息。无需为了 SEO 迁移 Next.js/Astro。

### 13.2 索引与 canonical

已发布且有独立价值的产品、比较、用途、教程可 index。内部搜索和无价值筛选 noindex；空态不造大量 URL。合法分页保留自己的 URL、自引用 canonical 与可抓取链接，不全部 canonical 到第一页。[W2]

`robots.txt` 用于爬取控制，不等于禁止索引或保密。需要 Google 看见 noindex 时不能同时阻止其抓取该页面。私有后台和预览必须用真正访问控制。[W5]

草稿不列 sitemap。lastmod 取实质内容更新，不取每日生成时间。合并重复文章使用适当跳转，不能拿 canonical 当万能去重按钮。改路由必须先做旧路由映射与无循环测试。

### 13.3 结构化数据与外链

文章使用与内容一致的 Article/NewsArticle，导航用 BreadcrumbList，组织信息必须真实。产品/软件结构化数据只在语义和要求匹配时使用；不伪造评分、价格、评论或承诺富结果展示。

商业链接标记 `rel="sponsored"`，必要时加 nofollow/noopener；标记不代替页面上的清楚商业披露。普通来源链接不得偷偷换成联盟链接。[W1]

### 13.4 缓存策略

公开已发布响应可短时共享缓存；后台、草稿、个性化及含认证响应禁止 CDN 公共缓存。发布事务生成变更记录，再清理产品、比较、类别和搜索相关缓存；故障时要有明确 TTL 上界。

建议初值：公共页面最多 5 分钟失效窗口，关键价格变更目标 60 秒内可见。它们是验收目标，不是当前实现能力。若未做精细 CDN 清除，先依靠短 TTL，不承诺瞬时更新。

## 14. 日本化与站内搜索

### 14.1 时区

持久化 UTC 时刻；所有站内自然日、周报分组、调度展示使用 Asia/Tokyo。不能只改 UI 标签。已有日本化改动必须核实而非重做；兼容旧函数名时文档说明，禁止同时出现 UTC+8 与 Tokyo 的混合业务日。

边界测试：`2026-10-04T14:59:59Z` 属于东京 10 月 4 日；`2026-10-04T15:00:00Z` 属于东京 10 月 5 日。另测月末、年末、周界，以及来源自带 offset 和仅日期文本。未知原时区不能静默假设中国时间。

### 14.2 搜索 V1

优先精确产品名 → 别名 → 用途/标题 → 摘要。对搜索用字段做 NFKC 与合理大小写规范化，原始显示文本不变。日语词和英文产品名通过人工别名表连接。

PostgreSQL 的全文配置与三元组相似度是可用工具，但不能直接等同于日语形态分析。短查询也可能没有足够三元组可用；使用有上限的子串回退并跑真实查询集。[W3、W4]

最小查询集 30 条，包含 `クロード`、`Claude`、全角英数、`議事録`、`PDF 要約`、两个字的词、产品旧称与无结果场景。至少预设每条应召回的产品/文档；不满足才考虑专门搜索服务或日语扩展，不预先购买。

## 15. 商业化、Newsletter 与分析

### 15.1 联盟与赞助

每项联盟计划记录：申请/获批状态、允许地区、允许 URL/渠道、重定向规则、归因期、结算定义、佣金和最后核验。不把尚未获批或不存在计划的产品收入计入预测。

外链中心统一管理，但不强制全部使用 /go。允许跳转时目标从数据库白名单读取；拒绝 query 传入任意 URL，防开放重定向。停用联盟链接后回官方链接，不改成无关高佣金商品。机器人、预取和 HEAD 不算有效用户点击。

赞助采用标明 PR 的稿件或独立位置；不购买自然排名、实测结论或评分。保留编辑方法与商业关系披露，政策由负责人在上线前确认。

### 15.2 周报

AIFIND Weekly 每周一次，初始结构可为 5 件变化、3 个值得试的产品、1 个实测工作流；信息不足不凑数。使用第三方服务完成订阅确认、退订、投递和 suppression list。AIFIND 保存期刊草稿与发送回执，不建立自营 SMTP。

发送流程：草稿 → 人工审核 → 测试收件人 → 明确发送操作 → 回执。重复任务不得发送两次；退订必须优先；开发/测试只能发受控地址。Newsletter 不是“自动发布所有草稿”。

### 15.3 指标定义

| 指标 | 口径 | 不能推导什么 |
| --- | --- | --- |
| qualified_outbound_sessions | 有真实页面交互后点击有效产品链接的会话数，剔除已知 bot/test/prefetch | 不等于用户数、购买或满意。 |
| outbound_rate | 上述会话数 / 产品决策相关页面会话数 | 不把全站 PV 当分母混用。 |
| affiliate_confirmed_revenue | 联盟最终确认且未撤销的收入 | 不是点击数量乘虚构单价。 |
| tutorial_task_feedback | 自愿回答已完成/未完成及问题 | 非代表性反馈，不能假称普遍成功率。 |
| newsletter_confirmed_signup | 已确认的新增订阅 | 不把表单提交算已订阅。 |
| content_freshness | 核心字段在复核期限内的覆盖情况 | 不说明内容绝对正确。 |

会话去重仅使用短期随机标识，并满足必要告知/同意，不使用跨站指纹。无法获得可靠会话口径时，只报告合格点击事件数，不伪称独立用户或会话数。

事件最少记录 product_view、compare_view、search、official_click、affiliate_click、newsletter_confirmed_signup。遵循适用同意与隐私要求；不暗中出售个人浏览行为。邮件打开率受客户端影响，只作辅助，优先看点击、退订和真实回复。

## 16. 安全、部署与运行维护

### 16.1 默认安全门

开发关闭 COLLECT_ENABLED、MODEL_CALLS_ENABLED、外部推送和索引提交；启用真实信源/模型/邮件前逐项确认。上游安全阀不一定阻止手动预览请求，因此费用测试必须明确隔离假服务和真实服务。[R1、R3–R4]

所有付费模型/抓取经过回执与预算控制。来源内容、提示词片段、JSON 和网页内指令一律当不可信数据；输出经过 schema、证据、业务校验。页面请求不得触发付费模型。

### 16.2 必须覆盖的攻击面

后台身份、CSRF、输入长度、限流与会话安全；Markdown 禁止任意 HTML/脚本/MDX，输出消毒；图片验证 MIME/尺寸/大小、移除敏感元数据、SVG 单独限制；外部抓取阻止私网/metadata 地址、限制重定向与响应体，防 SSRF。

预览/草稿不进公开缓存。SQL 参数化。日志清理密钥和个人信息。数据库不暴露公网；运行账户与迁移账户分离。上线初期管理员限定访问来源或额外网关保护，以环境能力选择。

### 16.3 部署最小拓扑

一个明确批准的运行环境承载 web/api/worker/PostgreSQL，进程分离但不拆微服务。无需先迁移云厂商。CDN 可选，不能替代原站鉴权。不得默认占用或修改现有代理/VPS、学习网站或其他项目网络配置。

图片从 P0 就必须持久化并可备份；可先使用绑定持久卷，规模/分发需要时再迁到 S3 兼容对象存储。不依赖容器临时磁盘。数据库和上传资产要能一起恢复。

### 16.4 备份与可观察性

上线前至少做一次隔离恢复演练。建议目标 RPO 24 小时、RTO 4 小时，只有实测达到后才对外承诺。备份加密、异地保存、受控保留；禁止将生产数据或密钥提交 Git。

监控 API 健康、worker 心跳、队列年龄、采集失败、模型花费、待审核年龄、过期字段、邮件失败和出站错误。失败不静默：模型停机可以保留已发布内容，不能随机降级到未经验证事实。

## 17. Codex 实施分期与验收门

### 17.1 Gate 0：只读基线核验

确认真实 repo 根目录、git HEAD/dirty state、AGENTS、lockfile、运行时、数据库迁移、模块插口、认证、出版范围、日文化补丁、媒体存储、实际路由与测试命令。输出复用/新增/最小核心改动矩阵。

## 19. 运营手册与内容健康度

日常工作从一个 Review Queue 开始，不从“今天生成多少文章”开始。优先级：关键事实错误 → 付费/安全告警 → 产品变化 → 当日精选 → 过期教程 → 新选题。

每个产品有负责人（V1 可是同一人）、核心字段清单、最近复核、下次复核、待复测关联页。核心价格最多 2 个工作日未处理的候选触发提醒；阈值可按实际容量调整，不能对外称实时保证。

每周回顾：新增与修订耗时、最慢任务、最常错字段、自然搜索进入的用户问题、商业点击、联盟真实收入与周报反馈。若维护债持续上升，暂停新增产品，而不是继续扩大目录。

产品下线保留有价值历史说明，不必立刻删除；清楚显示不可用并移除失效购买 CTA。被收购与停服分开。来源撤回触发复核，不自动断言原事实为假。

## 20. 商业可行性与预算模型

### 20.1 当前判断

值得验证的是“受控产品资料 + 实测教程 + 有选择的新闻入口”，不是“AIHOT 已经保证低成本流量”。没有用户、Search Console 与联盟回执之前，不能给成功率、市场份额或未来月入作确定结论。

优势假设：复用引擎降低基础开发量；单一事实库减少重复维护；日语任务验证与编辑选择形成实际增量。风险：获客慢、信息迅速过期、联盟不可得、人工验证不足、自研后台占用内容时间。每条假设都必须在 90 天实验中观察。

### 20.2 收入与成本公式

```text
广告收入 = 合格展示页面 PV / 1000 × 实际 Page RPM
联盟收入 = 商业意图会话 × 出站率 × 确认转化率
           × 每次确认转化净佣金
赞助收入 = 已签署且实际交付的赞助合同金额
贡献利润 = 确认收入 - 服务器/模型/邮件/订阅/外包直接成本
经济利润 = 贡献利润 - 负责人时间成本
```

不能把 PV、session、MAU 混用；不能把 signup 佣金与付费购买佣金混算。递延/撤销/退款按联盟回执处理。

纯教学算例：月会话 10,000，其中商业意图 30%，出站 20%，确认转化 3%，单次净佣金 1,500 日元，则联盟 27,000 日元。若可广告 PV 15,000、假设 Page RPM 300 日元，则广告 4,500 日元，合计 31,500 日元，尚未扣成本。这些全部是假设，不是日本费率、可达流量或收益预测；没有获批联盟计划时相应收入为零。

### 20.3 预算控制

开发测试默认零外部采集/模型开销。负责人另行批准月度预算后，分别设基础设施、模型、测试产品订阅、邮件、内容外包上限；达到 80% 提示、达到上限停止相关付费任务。页面仍服务已发布内容。

不为首年预买大量域名、广告、模型套餐或搜索服务。不因为曾投入 AIHOT 就忽略总机会成本；自研后台的投入必须与可复用编辑能力比较。

## 21. 路线、KPI 与继续条件

### 21.1 90 天执行

第 1–2 周：Gate 0、品牌门禁、一个产品完整闭环和一个教程完整闭环。第 3–4 周：8–12 产品、3 比较、6 教程、3 用途页，稳定新闻入口与真实搜索/分析接入。

第 2 月：在两个主题簇内完善限制、价格和实测内容，开通经同意的周报，核验少量联盟资格。第 3 月：以 20–30 产品、8–10 比较、6–8 用途、18–24 教程作为基准产能目标；质量/维护通过才扩大。

6 个月评估获胜主题和单位维护成本，不机械扩到数百页。12 个月只有在回访、编辑容量和经济性支持时增加一个选择/成本工具；不同时恢复企业数据库、App 与多语言。

### 21.2 判断门

| 维度 | GO / 继续 | ITERATE / 调整 | 暂停扩张 |
| --- | --- | --- | --- |
| 数据质量 | 核心事实均有证据、无已知严重错误、修改能追溯 | 过期项和误抽取集中于少数字段 | 草稿泄露、错误价格、证据不可追溯未修复。 |
| 用户任务 | 实际用户能完成找工具/比较/教程任务 | 有阅读但无法完成下一步 | 完全无人使用核心功能，需重访需求。 |
| 获客 | 若干常青页的相关查询和点击持续出现 | 仅新闻峰值或查询不匹配 | 6 个月有充分质量投入仍无可复现获客路径。 |
| 商业 | 有合法项目、有效点击与可核对首批收入 | 点击有、转化不足或佣金经济性不成立 | 只有曝光，无商业意图和非广告需求。 |
| 维护 | 复核与内容投入在工时上限内 | 积压上升，需缩减产品数 | 无法承担，先停止扩目录而非继续堆量。 |

这些是内部管理条件，不能以“90 天 Google 没排名”单一指标断言项目必败。访谈与手动用户实验可以先于自然搜索规模。建议先找 8–12 位目标用户做具体任务观察；小样本只用于发现问题，不冒充统计成功率。
